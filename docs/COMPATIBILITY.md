## Compatibility matrix

`CLIENT BLOCKER` means a confirmed client path would break, not that every client needs that feature. `CUTOVER BLOCKER` means that dependency must be resolved **or explicitly retired** before C; it does not require preserving the old API forever. `MIGRATION` covers conversion/client changes; `INTENTIONAL` covers acceptable narrower behavior; `UNKNOWN` marks missing operational evidence. A dash means compatible for the inspected use, not universal equivalence.

## Milestone gates

### A — independent CFLab at `cflab.aismallbizguru.com`

**No new application-code DEPLOY BLOCKER was found.** The remaining deployment prerequisites are real, not compatibility requirements: verified Cloudflare account/active zone and unoccupied intended hostname, creation/ownership verification of dedicated resources, replacing the all-zero D1 ID, local verification, remote initial migrations, and deliberate publication from [DEPLOYMENT.md](DEPLOYMENT.md). No resource or remote state is claimed verified by this source audit.

Isolation checks (C3/L4/L7):

- Production config targets only Worker/D1 `cflab`, R2 `cflab-files`, and the exact `cflab` Custom Domain. Legacy examples use local SQLite, MinIO `labbox-assets`, and R2 backups `lab-aismallbizguru-backups`. No configured namespace collision found.
- `npm run db:migrate` explicitly uses local config and `--local`. Build is a dry run; CI only installs/checks/local-migrates/builds. Deployment instructions use explicit production config, binding `DB`, and `--no-x-provision`. No LabBox importer or destructive migration tooling exists here.
- Config cannot prevent an operator inserting the wrong account/database ID or reusing an unrelated bucket. The account and resource IDs were subsequently verified and pinned; ownership must still be rechecked before any future resource change. If any configured resource belongs to LabBox, that is a **DEPLOY BLOCKER**—stop rather than overwrite. No current evidence of that collision exists.
- Production admin requires an active human administrator session; the local entrypoint keeps a separate loopback development secret, and proxies default off. Human authentication does not weaken machine-token checks or prevent liveness/read/write operation with provisioned data.
- Application code is hostname-independent. C reuses these same bindings/resources; only approved routing/host-bound configuration should change.

### B — first pilot: Wildlife Pattern Lab, read-only

Before acceptance: adapt the P client routes, consume every page for both resources before committing IndexedDB changes, show CFLab errors, and replace the health-first browser diagnostic with an authenticated scoped read. Test more than 100 records, reordered rows, an empty resource, and a second-page failure preserving the previous cache.

Provision only the wildlife app, exact frontend origin, and a fresh `records:read` token. Seed an agreed, authorized snapshot of observations/trips preserving IDs, nested JSON, timestamps, and internal references. Keep precise locations private. Verify data mapping, counts, and representative payloads with offline fixtures before any approved import. A bounded read-only pilot may be a dated snapshot; a live-feed pilot still needs a deliberate refresh/delta process while WFR writes to LabBox. Never imply the GET harness synchronizes data.

**Admin distinction:** local admin writes only local D1; it cannot seed a deployed Worker. CFLab now provides human administrator sessions and an admin API/UI for remote user, app, and token provisioning ([AUTH.md](AUTH.md)); a narrowly scoped operator bootstrap through Cloudflare account-authenticated tooling remains available for the first administrator or direct D1 work, storing only hashes, never plaintext tokens. Never expose local admin in production or copy an entire local DB with development credentials. Token revocation must remain operable through the chosen process.

### C — eventually route `lab.aismallbizguru.com` to CFLab

Account for all P/W/T and A consumers first. Route/token/public-file/collection differences are cutover blockers only while such clients still depend on them. Analytics is demonstrably used and cannot silently disappear. Old absolute `/api/files/:id` references embedded in records, pages, browser caches, or external links need rewriting or a narrowly tested legacy file mapping with the intended authorization policy; replacing a hostname alone is insufficient.

Complete ID/reference mapping, object integrity checks, final legacy write reconciliation, recovery rehearsal, retention decisions, and rollback accounting for new CFLab writes. Confirm the deployed LabBox revision and additional automation/clients before declaring coverage complete. Review browser caches/service workers and long-lived saved tokens/configurations. Preserve WFR's local/offline state; don't reset it indiscriminately.

Keep the **existing CFLab Worker/D1/R2**. With API/data migration already accepted, C should be primarily hostname routing, certificates, host-bound Access policies, and monitoring updates; retain `cflab` for migrated clients. The hostname itself is not an API incompatibility. No new production stack is required or recommended.

## What not to port

For the identified clients, there is no evidence requiring the legacy public registry/schema UI, creator-token response fields, specialized trip aggregation, unlimited server lists, server-calculated totals, custom password/session system, proxy caching/header configuration that never affected fetches, or VPS job framework. Keep these out of the first implementation pass. Server chronological ordering can be replaced by deterministic client sorting after complete pagination. Backup outcomes still matter even when backup implementation changes.

Never preserve cross-app mutation gaps, unrestricted token defaults, or error-detail leakage. These are intentional removals, not migration obligations. **Do not discard** anonymous Top Hat content, file associations/image fallback outcomes, analytics ingestion/dashboard, or retention guarantees without deliberate consumer/operator decisions. “No caller found” is not proof of absence outside the searched source; operational jobs/proxy users still need operator confirmation before retirement.

## Harness scope and safe operation

The existing [GET-only harness](../test/remote/compat.remote.mjs) was extended, not replaced. It remains separate from normal local tests/CI and has no default targets. It refuses redirects, cross-origin paths, insecure remote URLs, unsafe identifiers, and unbounded responses. It prints neither payloads nor tokens.

- CFLab health is checked by default after explicit target configuration. **Legacy health is skipped** unless `COMPAT_LABBOX_HEALTH=1`. First confirm deployed `STORAGE_HEALTH_ENABLED=false`: L4 health calls `ensure_bucket_exists()`, which can call MinIO `make_bucket`. GET is not inherently non-mutating. Do not enable this probe merely to remove a skip.
